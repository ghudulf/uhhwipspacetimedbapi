# Design Document: SpacetimeDB 2.0 Migration

## Overview

This design document outlines the technical approach for migrating the BRU-AVTOPARK bus ticket sales system from SpacetimeDB 1.0 to 2.0. The migration involves updating the server module (C# WASM), client services (C# .NET), and adapting to the new event-driven architecture introduced in 2.0.

The system consists of:
- **Server Module** (`server/` directory): C# WASM module with tables and reducers for authentication, bus management, routes, tickets, and sales
- **API Service** (`BRU-AVTOPARK-AspireAPI/`): ASP.NET Core API that wraps SpacetimeDB functionality
- **Avalonia Desktop Client** (`BRU.Avtopark.TicketSalesAPP.Avalonia.Unity/`): Desktop application for ticket sales and management

### Custom Authentication System

**Important Context**: This system uses a custom authentication layer built on top of SpacetimeDB because SpacetimeDB 1.2.1 had zero support for role-based authentication. The ASP.NET API acts as middleware between clients and SpacetimeDB, handling:

1. **JWT Token Generation**: The API generates JWT tokens with claims including login field and user roles
2. **Role-Based Access Control**: Controllers check roles based on JWT claims
3. **Identity Management**: Custom identity generation using SpacetimeDB's HTTP identity endpoint
4. **Multiple Authentication Methods**: Support for password, QR code, two-factor, magic link, and WebAuthn

**Architecture Pattern**:
```
Avalonia Client → HTTP POST → ASP.NET API → SpacetimeDB
                              (JWT Auth)     (Identity + Roles)
```

The API stores all auth data in SpacetimeDB tables (UserProfile, Role, Permission, UserRole, RolePermission) and associates JWT tokens with SpacetimeDB identities. This allows the API to act as an authentication gateway while SpacetimeDB handles data storage and real-time synchronization.

**Key Challenge**: Identity generation was "a pain" - had to jerry-rig a solution using the HTTP identity endpoint with temporary random JWT tokens to output unique identities instead of reusing the API server's identity.

**1.0 Characteristics:**
- ASP.NET API acts as authentication middleware
- JWT tokens generated by API with role claims
- SpacetimeDB stores user data and roles
- Custom identity generation via HTTP endpoint
- Reducer callbacks broadcast to all subscribers
- `WithDatabaseName()` for connection
- Light mode to suppress reducer events
- `CallReducerFlags` for fine-grained control
- Reducer arguments exposed to subscribers

**Authentication Flow (1.0)**:
1. Client sends login credentials to API via HTTP POST
2. API calls SpacetimeDB reducer to verify credentials
3. API generates JWT token with user roles and SpacetimeDB identity
4. Client stores JWT token in memory (non-persistent)
5. Client includes JWT token in all subsequent API requests
6. API validates JWT and checks roles before calling SpacetimeDB reducers

1. Client sends login credentials to API via HTTP POST
2. API calls SpacetimeDB reducer to verify credentials
3. API generates JWT token with user roles and SpacetimeDB identity
4. Client stores JWT token in memory
5. Client includes JWT token in all subsequent API requests
6. API validates JWT and checks roles before calling SpacetimeDB reducers

**Key Migration Note**: The custom authentication system built for 1.2.1 will continue to work in 2.0 with minimal changes. The main updates are to the SpacetimeDB SDK API (connection, subscriptions, events), not to the authentication architecture itself.

## Components and Interfaces

### 0. Authentication System (Critical Context)

The authentication system is a custom implementation built on top of SpacetimeDB because version 1.2.1 lacked role-based access control. This system must be preserved during the 2.0 migration.

#### JWT Token Generation

The API generates JWT tokens with custom claims:

```csharp
// AuthController.cs - GenerateJwtToken method
private string GenerateJwtToken(User user) {
    var role = _spacetimeDBService.GetConnection().Db.Role.RoleId.Find(user.RoleId);
    
    var claims = new[] {
        new Claim(JwtRegisteredClaimNames.Sub, user.Login),
        new Claim("userId", user.UserId.ToString()),
        new Claim("identity", user.Identity.ToString()),  // SpacetimeDB Identity
        new Claim(ClaimTypes.Role, role?.Name ?? "User"),
        new Claim("roleId", user.RoleId.ToString())
    };
    
    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_configuration["Jwt:Key"]));
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
    
    var token = new JwtSecurityToken(
        issuer: _configuration["Jwt:Issuer"],
        audience: _configuration["Jwt:Audience"],
        claims: claims,
        expires: DateTime.Now.AddHours(24),
        signingCredentials: creds
    );
    
    return new JwtSecurityTokenHandler().WriteToken(token);
}
```

#### Identity Generation Pattern

**Challenge**: SpacetimeDB identities are tied to connections. When the API server connects, it gets one identity. But we need unique identities for each user.

**Solution**: Use SpacetimeDB's HTTP identity endpoint to generate new identities:

```csharp
// During user registration
public async Task<Identity> GenerateNewIdentity() {
    var httpClient = new HttpClient();
    var response = await httpClient.PostAsync(
        "http://localhost:3000/v1/identity",
        new StringContent("{}", Encoding.UTF8, "application/json")
    );
    
    var result = await response.Content.ReadFromJsonAsync<IdentityResponse>();
    return result.Identity;
}
```

#### Role-Based Access Control

The API enforces role-based access control via JWT claims:

```csharp
// Controller authorization
[Authorize(Roles = "Administrator")]
[HttpPost("register")]
public async Task<ActionResult> RegisterUser([FromBody] RegisterModel model) {
    // Only administrators can register users
    var identity = await GenerateNewIdentity();
    
    // Call SpacetimeDB reducer to create user
    _spacetimeDBService.EnqueueCommand("registeruser", new Dictionary<string, object> {
        { "login", model.Login },
        { "password", model.Password },
        { "email", model.Email },
        { "phoneNumber", model.PhoneNumber },
        { "roleId", model.RoleId }
    });
    
    return Ok();
}
```

#### Authentication Methods Supported

1. **Password Authentication**: Standard login/password with PBKDF2 hashing
2. **QR Code Authentication**: Generate QR codes for mobile device login
3. **Two-Factor Authentication (TOTP)**: Time-based one-time passwords
4. **Magic Link**: Email-based passwordless authentication
5. **WebAuthn**: Hardware security key support

#### Migration Impact

**What Stays the Same**:
- JWT token generation and validation
- Role-based access control in controllers
- Identity generation pattern
- Authentication method implementations
- Password hashing (PBKDF2 with SHA-256)

**What Changes**:
- SpacetimeDB SDK API calls (`WithDatabaseName` → `WithDatabaseName`)
- Event handling (remove reducer callbacks, add event tables)
- Subscription patterns (explicit event table subscriptions)

**Known Issues to Address**:

1. **JSON Parsing Challenges**: The current implementation has complex JSON parsing issues when deserializing SpacetimeDB responses through the ASP.NET API. The JSON contains `$id` and `$values` metadata that requires custom handling:

```csharp
// Example of problematic JSON structure
{
  "$id": "1",
  "$values": [
    {
      "$id": "2",
      "busId": 1,
      "model": "МАЗ-303E10",
      "registrationNumber": "AB 1001 7",
      "capacity": 82,
      "isActive": true
    },
    // ... more items
  ]
}
```

**Current Workaround**: Manual JSON parsing with custom deserializers to handle the `$id` and `$values` structure. This is a "nightmare" to maintain and should be refactored.

**Recommended Solution for 2.0**: 
- Consider using SpacetimeDB's typed query builder on the client side
- Simplify JSON serialization by avoiding nested object references
- Use DTOs (Data Transfer Objects) for API responses instead of direct SpacetimeDB table types
- Implement custom JsonConverter for SpacetimeDB types if needed

2. **Missing Fields**: Some fields are not displaying correctly due to JSON parsing issues. This needs to be debugged and fixed during migration.

3. **Non-Persistent Login**: Login state is not persistent (cleared on application close). This should be addressed by implementing secure token storage.

### 1. Server Module Updates

#### Package Dependencies

**Current (1.0):**
```xml
<PackageReference Include="SpacetimeDB.Runtime" Version="1.2.1" />
```

**Target (2.0):**
```xml
<PackageReference Include="SpacetimeDB.Runtime" Version="2.0.0" />
```

#### Table Definitions

Tables remain largely unchanged, but we need to ensure proper attribute usage:

```csharp
// Existing tables work as-is
[SpacetimeDB.Table(Public = true)]
public partial class UserProfile {
    [PrimaryKey, AutoInc]
    public uint UserId;
    
    [Unique]
    public Identity Identity;
    
    public string Login;
    public string PasswordHash;
    // ... other fields
}
```

**Key Points:**
- `[SpacetimeDB.Table]` attribute syntax unchanged
- `Public = true` still controls visibility
- Primary keys and unique constraints work the same
- Only primary key columns get `Update()` methods

#### Event Tables (New in 2.0)

Event tables are the replacement for reducer callbacks. They publish transient events to subscribers:

```csharp
// Event table for authentication events
[SpacetimeDB.Table(Event = true, Public = true)]
public partial class AuthenticationEvent {
    public Identity UserId;
    public string EventType;  // "Login", "Logout", "Failed"
    public ulong Timestamp;
    public string? Details;
}

// Event table for ticket sales
[SpacetimeDB.Table(Event = true, Public = true)]
public partial class TicketSaleEvent {
    public uint SaleId;
    public uint TicketId;
    public Identity BuyerId;
    public double Amount;
    public ulong Timestamp;
}

// Event table for bus status changes
[SpacetimeDB.Table(Event = true, Public = true)]
public partial class BusStatusEvent {
    public uint BusId;
    public string Status;  // "Active", "Inactive", "Maintenance"
    public ulong Timestamp;
    public Identity ChangedBy;
}
```

**Event Table Characteristics:**
- Marked with `Event = true` in the `[SpacetimeDB.Table]` attribute
- Always empty outside of a transaction
- Only `OnInsert` callbacks are generated (no `OnDelete` or `OnUpdate`)
- Must be explicitly subscribed to (excluded from `SubscribeToAllTables()`)
- Published only if the transaction commits

#### Reducer Updates

Reducers need minimal changes, but we add event publishing:

```csharp
[SpacetimeDB.Reducer]
public static void AuthenticateUser(ReducerContext ctx, string login, string password) {
    var user = ctx.Db.UserProfile.Login.Find(login);
    
    if (user == null) {
        // Publish failed authentication event
        ctx.Db.AuthenticationEvent.Insert(new AuthenticationEvent {
            UserId = Identity.Default,
            EventType = "Failed",
            Timestamp = (ulong)ctx.Timestamp.MicrosecondsSinceUnixEpoch / 1000,
            Details = "User not found"
        });
        throw new Exception("Invalid credentials");
    }
    
    if (!VerifyPassword(password, user.PasswordHash)) {
        // Publish failed authentication event
        ctx.Db.AuthenticationEvent.Insert(new AuthenticationEvent {
            UserId = user.Identity,
            EventType = "Failed",
            Timestamp = (ulong)ctx.Timestamp.MicrosecondsSinceUnixEpoch / 1000,
            Details = "Invalid password"
        });
        throw new Exception("Invalid credentials");
    }
    
    // Publish successful authentication event
    ctx.Db.AuthenticationEvent.Insert(new AuthenticationEvent {
        UserId = user.Identity,
        EventType = "Login",
        Timestamp = (ulong)ctx.Timestamp.MicrosecondsSinceUnixEpoch / 1000,
        Details = null
    });
    
    Log.Info($"User {login} authenticated successfully");
}
```

**Key Changes:**
- Insert into event tables to notify subscribers
- Events only published if reducer succeeds (transaction commits)
- No need to manually check `ctx.Sender == ctx.Identity` for scheduled reducers (they're private by default in 2.0)

#### Scheduled Reducer Security

Scheduled reducers are now private by default:

```csharp
// 1.0 - Manual authorization check (NO LONGER NEEDED)
[SpacetimeDB.Reducer]
public static void ProcessScheduledTask(ReducerContext ctx, ScheduledTask task) {
    if (ctx.Sender != ctx.Identity) {
        throw new Exception("Only the scheduler can call this");
    }
    // Process task...
}

// 2.0 - Private by default, no check needed
[SpacetimeDB.Reducer]
public static void ProcessScheduledTask(ReducerContext ctx, ScheduledTask task) {
    // Process task...
    // Only the database itself can invoke this
}
```

If a scheduled reducer needs to be callable by clients, create a public wrapper:

```csharp
// Private scheduled reducer
[SpacetimeDB.Reducer]
private static void ProcessScheduledTaskInternal(ReducerContext ctx, ScheduledTask task) {
    // Implementation
}

// Public wrapper
[SpacetimeDB.Reducer]
public static void ProcessScheduledTask(ReducerContext ctx, ScheduledTask task) {
    ProcessScheduledTaskInternal(ctx, task);
}
```

### 2. Client Service Updates

#### Connection Builder

**Current (1.0):**
```csharp
_connection = DbConnection.Builder()
    .WithUri(host)
    .WithDatabaseName(moduleName)  // OLD API
    .WithToken(AuthToken.Token)
    .WithLightMode(true)  // REMOVED in 2.0
    .OnConnect(OnConnected)
    .OnConnectError(OnConnectError)
    .OnDisconnect(OnDisconnected)
    .Build();
```

**Target (2.0):**
```csharp
_connection = DbConnection.Builder()
    .WithUri(host)
    .WithDatabaseName(databaseName)  // NEW API
    .WithToken(AuthToken.Token)
    .WithConfirmedReads(true)  // Optional, true by default
    .OnConnect(OnConnected)
    .OnConnectError(OnConnectError)
    .OnDisconnect(OnDisconnected)
    .Build();
```

**Key Changes:**
- `WithDatabaseName()` → `WithDatabaseName()`
- Remove `WithLightMode()` (no longer needed)
- Add `WithConfirmedReads()` if you want to opt out of confirmed reads

#### Subscription Updates

**Current (1.0):**
```csharp
_connection.SubscriptionBuilder()
    .OnApplied(OnSubscriptionApplied)
    .OnError(OnSubscriptionError)
    .SubscribeToAllTables();
```

**Target (2.0):**
```csharp
// Subscribe to regular tables
_connection.SubscriptionBuilder()
    .OnApplied(OnSubscriptionApplied)
    .OnError(OnSubscriptionError)
    .SubscribeToAllTables();

// Subscribe to event tables explicitly
_connection.SubscriptionBuilder()
    .OnApplied(ctx => Log.Info("Event subscription applied"))
    .OnError((ctx, err) => Log.Error($"Event subscription error: {err}"))
    .Subscribe(new[] {
        "SELECT * FROM AuthenticationEvent",
        "SELECT * FROM TicketSaleEvent",
        "SELECT * FROM BusStatusEvent"
    });
```

**Key Changes:**
- Event tables must be subscribed to explicitly
- Event tables are excluded from `SubscribeToAllTables()`
- Can use typed query builder for subscriptions (recommended)

#### Event Handling

**Current (1.0):**
```csharp
// Global reducer callbacks (REMOVED in 2.0)
_connection.Reducers.OnAuthenticateUser += (ctx, args) => {
    Console.WriteLine($"Someone authenticated: {args.login}");
};
```

**Target (2.0):**
```csharp
// Per-call result handling
try {
    await _connection.Reducers.AuthenticateUser(login, password);
    Console.WriteLine("Authentication successful");
} catch (Exception ex) {
    Console.WriteLine($"Authentication failed: {ex.Message}");
}

// Event table callbacks for cross-client notifications
_connection.Db.AuthenticationEvent.OnInsert += (ctx, evt) => {
    if (evt.EventType == "Login") {
        Console.WriteLine($"User logged in: {evt.UserId}");
    } else if (evt.EventType == "Failed") {
        Console.WriteLine($"Login failed: {evt.Details}");
    }
};
```

**Key Changes:**
- No more global reducer callbacks
- Use `await` or `_then()` for own reducer results
- Use event table `OnInsert` callbacks for cross-client notifications
- Event context has `tag` property: `Reducer`, `Transaction`, `SubscribeApplied`, `UnsubscribeApplied`, `SubscribeError`

#### Table Callbacks

Table callbacks work similarly, but the event context is different:

```csharp
// 1.0 and 2.0 - Similar syntax
_connection.Db.UserProfile.OnInsert += (ctx, user) => {
    // Check what caused this insert
    if (ctx.Event.tag == "Reducer") {
        // This client called a reducer that inserted this row
        var reducerEvent = ctx.Event.value;
        Console.WriteLine($"Our reducer: {reducerEvent.reducer}");
    } else if (ctx.Event.tag == "Transaction") {
        // Another client's action caused this insert
        Console.WriteLine("Another client inserted a user");
    } else if (ctx.Event.tag == "SubscribeApplied") {
        // This row was inserted due to a new subscription
        Console.WriteLine("Subscription applied");
    }
};
```

**Key Changes:**
- `UnknownTransaction` event removed
- Event has `tag` property instead of discriminated union
- Reducer events only contain metadata for the calling client

### 3. Code Generation

#### Overview

Before interacting with a SpacetimeDB database from a client application, you must generate client bindings for your module. These bindings create type-safe interfaces that allow your client to query tables, invoke reducers, call procedures, and subscribe to tables and/or views.

#### What Are Module Bindings?

Module bindings are auto-generated code that mirrors your module's schema and functions. They provide:

- **Type definitions** matching your module's tables and types
- **Callable functions** for invoking reducers and procedures
- **Query interfaces** for subscriptions and local cache access
- **Callback registration** for observing database changes

The bindings ensure compile-time type safety between your client and server code, catching errors before runtime.

#### Generating Bindings

**Current (1.0):**
```bash
spacetime generate --lang cs --out-dir module_bindings
```

**Target (2.0):**
```bash
# Default: excludes private tables/functions
spacetime generate --lang cs --out-dir module_bindings --module-path server/

# Include private items if needed
spacetime generate --lang cs --out-dir module_bindings --module-path server/ --include-private
```

**Key Changes:**
- Private tables and functions excluded by default in 2.0
- Use `--include-private` flag if client needs access to private items
- `--module-path` parameter points to the directory containing `.csproj` file

#### What Gets Generated

The `spacetime generate` command creates client-side representations of your module's components:

**Tables:**
For each table in your module, codegen generates:
- Type/class definitions with properties for each column
- Table accessor on the `DbConnection` for querying the client cache
- Callback registration methods for observing insertions, updates, and deletions

Example for a `User` table:
```csharp
// Generated type
public partial class User {
    public ulong Id;
    public string Name;
    public string Email;
}

// Access via DbConnection
conn.Db.User  // Table accessor

// Callbacks
conn.Db.User.OnInsert += (ctx, user) => { /* ... */ };
conn.Db.User.OnUpdate += (ctx, oldUser, newUser) => { /* ... */ };
conn.Db.User.OnDelete += (ctx, user) => { /* ... */ };
```

**Reducers:**
For each reducer in your module, codegen generates:
- Client-callable function that sends a reducer invocation request to the server
- Type-safe parameters matching the reducer's signature

Example for a `CreateUser` reducer:
```csharp
// Call the reducer
conn.Reducers.CreateUser(name, email);

// With await (2.0)
await conn.Reducers.CreateUser(name, email);
```

**Note:** In 2.0, global reducer callbacks (`OnCreateUser`) are removed. Use `await` for own reducer results or event tables for cross-client notifications.

**Procedures (Beta):**
For each procedure in your module, codegen generates:
- Client-callable function that invokes the procedure
- Return value handling for procedures that return results
- Type-safe parameters matching the procedure's signature

Example for a `FetchExternalData` procedure:
```csharp
// Call the procedure
var result = await conn.Procedures.FetchExternalData(url);
```

**Views:**
For each view in your module, codegen generates:
- Type definitions for the view's return type
- Subscription interfaces for subscribing to view results
- Query methods for accessing cached view results

Views provide subscribable, computed queries over your data.

**Event Tables (New in 2.0):**
For each event table in your module, codegen generates:
- Type definitions for the event structure
- `OnInsert` callback registration (only insert, no update/delete)
- Subscription interfaces (must be explicitly subscribed)

Example for an `AuthenticationEvent` table:
```csharp
// Subscribe to event table explicitly
conn.SubscriptionBuilder()
    .Subscribe(new[] { "SELECT * FROM AuthenticationEvent" });

// Register callback
conn.Db.AuthenticationEvent.OnInsert += (ctx, evt) => {
    Console.WriteLine($"Auth event: {evt.EventType}");
};
```

#### Regenerating Bindings

Whenever you modify your module's schema or function signatures, regenerate the client bindings by running `spacetime generate` again. The tool will overwrite the existing generated files with updated code.

**Best Practice:** Add `spacetime generate` to your build or development workflow if you're actively developing and testing changes.

#### Using the Generated Code

Once you've generated the bindings, import them in your client application:

```csharp
// The generated bindings are typically in a namespace matching your module
using YourModuleName;

// Connect to the database
var conn = DbConnection.Builder()
    .WithUri("http://localhost:3000")
    .WithDatabaseName("your-database")
    .Build();

// Access tables
var users = conn.Db.User;

// Call reducers
await conn.Reducers.CreateUser("Alice", "alice@example.com");

// Subscribe to changes
conn.Db.User.OnInsert += (ctx, user) => {
    Console.WriteLine($"New user: {user.Name}");
};
```

#### Troubleshooting

**Missing module directory:**
If `spacetime generate` fails to find your module, ensure you're pointing to the directory containing your module's `.csproj` file:

```bash
# Correct - points to directory with .csproj
spacetime generate --lang cs --out-dir module_bindings --module-path server/

# Incorrect - missing module path
spacetime generate --lang cs --out-dir module_bindings
```

**Outdated bindings:**
If your client doesn't see new tables or reducers, ensure you've regenerated the bindings after updating your module. Generated code is not automatically updated when the module changes.

**Private items not visible:**
If you need access to private tables or reducers in your client, use the `--include-private` flag:

```bash
spacetime generate --lang cs --out-dir module_bindings --module-path server/ --include-private
```

#### Migration-Specific Notes

**For Your Project:**

1. **Current "Jerry-Rigged" Setup**: 
   - SpacetimeDB generates bindings at the project root by default
   - You've been manually copying bindings to `BRU-AVTOPARK-AspireAPI/TicketSalesApp.Services/client/module_bindings/`
   - This is necessary because the API service project needs access to the generated types
   - The manual copy process is error-prone and easy to forget

2. **Better Solution for 2.0**: Use `--out-dir` to generate directly into the service project:
   ```bash
   # Generate bindings directly into the API service project
   spacetime generate --lang cs \
     --out-dir BRU-AVTOPARK-AspireAPI/TicketSalesApp.Services/client/module_bindings \
     --module-path server/
   ```

3. **Automated Build Integration**: Add this to your build process to eliminate manual copying:
   ```xml
   <!-- In TicketSalesApp.Services.csproj -->
   <Target Name="GenerateSpacetimeBindings" BeforeTargets="BeforeBuild">
     <Exec Command="spacetime generate --lang cs --out-dir client/module_bindings --module-path ../../server/" 
           WorkingDirectory="$(ProjectDir)" />
   </Target>
   ```
   
   Or use a pre-build script:
   ```bash
   # scripts/generate-bindings.sh
   #!/bin/bash
   cd "$(dirname "$0")/.."
   spacetime generate --lang cs \
     --out-dir BRU-AVTOPARK-AspireAPI/TicketSalesApp.Services/client/module_bindings \
     --module-path server/
   ```

4. **Current Binding Location**: 
   - Path: `BRU-AVTOPARK-AspireAPI/TicketSalesApp.Services/client/module_bindings/`
   - Contains: `Reducers/`, `Tables/`, `Types/`, `SpacetimeDBClient.cs`, and other generated files
   - These files are referenced by `SpacetimeDBService.cs` and other service implementations

5. **Event Tables**: After defining event tables in your module, regenerate bindings to get the event table types and `OnInsert` callbacks. Remember to generate into the correct directory.

6. **Reducer Callbacks**: The generated code in 2.0 will NOT include `OnReducerName` callback methods. This is intentional - use `await` or event tables instead.

7. **Migration Checklist for Bindings**:
   - [ ] Update generation command to use `--out-dir` pointing to service project

### Event Publishing Pattern

Reducers should publish events at appropriate points:

```csharp
[SpacetimeDB.Reducer]
public static void CreateTicketSale(ReducerContext ctx, uint ticketId, uint routeId, double amount, string paymentMethod) {
    // Validate and create sale
    var saleId = GetNextId(ctx, "saleId");
    var sale = new TicketSale {
        SaleId = saleId,
        TicketId = ticketId,
        RouteId = routeId,
        BuyerId = ctx.Sender,
        Amount = amount,
        PaymentMethod = paymentMethod,
        Timestamp = (ulong)ctx.Timestamp.MicrosecondsSinceUnixEpoch / 1000
    };
    ctx.Db.TicketSale.Insert(sale);
    
    // Publish event for subscribers
    ctx.Db.TicketSaleEvent.Insert(new TicketSaleEvent {
        SaleId = saleId,
        TicketId = ticketId,
        RouteId = routeId,
        BuyerId = ctx.Sender,
        Amount = amount,
        Timestamp = sale.Timestamp,
        PaymentMethod = paymentMethod
    });
    
    Log.Info($"Ticket sale created: {saleId}");
}
```

## Correctness Properties

A property is a characteristic or behavior that should hold true across all valid executions of a system - essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.


### Property 1: Reducer Execution Success

*For any* reducer defined in the module, when it is called with valid arguments, the reducer should execute successfully and return results to the caller.

**Validates: Requirements 12.3**

### Property 2: Table Update Notifications

*For any* subscribed table, when a row is inserted, updated, or deleted, the corresponding callback (OnInsert, OnUpdate, or OnDelete) should be invoked with the correct event context.

**Validates: Requirements 12.4**

### Property 3: Event Table Notifications

*For any* event table, when an event is published (inserted) during a successful transaction, the OnInsert callback should be invoked for all subscribed clients.

**Validates: Requirements 12.5**

### Property 4: Event Context Tag Correctness

*For any* table callback triggered by the calling client's own reducer, the event context should have tag "Reducer" with full reducer information.

**Validates: Requirements 7.1**

## Error Handling

### Migration Errors

**Package Version Mismatch:**
- **Error**: Build fails with package resolution errors
- **Cause**: SpacetimeDB.Runtime version mismatch between module and client
- **Solution**: Ensure all projects reference the same 2.0.x version

**Connection Failures:**
- **Error**: `DbConnection.Build()` throws exception
- **Cause**: Using old API (`WithDatabaseName`) or incorrect database name
- **Solution**: Update to `WithDatabaseName()` and verify database name is correct

**Subscription Errors:**
- **Error**: Event table subscriptions not receiving events
- **Cause**: Event tables not explicitly subscribed (excluded from `SubscribeToAllTables()`)
- **Solution**: Add explicit subscription for each event table

**Reducer Call Errors:**
- **Error**: Reducer callbacks not firing
- **Cause**: Using old 1.0 reducer callback pattern (`OnReducerName`)
- **Solution**: Remove global reducer callbacks, use `await` or event tables

### Runtime Errors

**Transaction Rollback:**
- **Error**: Reducer throws exception, changes not persisted
- **Cause**: Validation failure or business logic error
- **Solution**: Ensure proper error handling and validation before modifying tables

**Event Publishing Failures:**
- **Error**: Events not received by subscribers
- **Cause**: Transaction rolled back before commit, or event table not subscribed
- **Solution**: Ensure reducer succeeds and clients have explicit event table subscriptions

**Index Access Errors:**
- **Error**: `Update()` method not available on unique column
- **Cause**: Trying to update via non-primary-key unique constraint
- **Solution**: Use delete-then-insert pattern for non-primary-key unique columns

### Deployment Errors

**Module Publish Failures:**
- **Error**: `spacetime publish` fails with schema migration error
- **Cause**: Incompatible schema changes (removing columns, changing types)
- **Solution**: Use `--delete-data` flag during development, or implement incremental migration pattern

**Code Generation Errors:**
- **Error**: Generated bindings missing expected types
- **Cause**: Private tables/functions excluded by default in 2.0
- **Solution**: Use `--include-private` flag if client needs access to private items

### Performance Considerations

**Confirmed Reads (Default in 2.0):**
- Adds a few milliseconds of latency for durability
- Ensures clients never see data that could be lost on crash
- Can opt out with `WithConfirmedReads(false)` if low latency is critical

**Event Tables:**
- More efficient than 1.0 reducer callbacks (no broadcasting of reducer arguments)
- Only subscribed clients receive events
- Events are transactional (only published if transaction commits)

**In-Memory Database:**
- SpacetimeDB holds all data in memory for sub-microsecond access
- Persists to commit log for durability
- Faster than traditional databases for real-time applications

### Security Improvements

**Scheduled Reducers:**
- Private by default in 2.0 (only callable by database itself)
- No need for manual authorization checks
- Prevents accidental exposure of scheduled functions

**Event Tables:**
- You control exactly what data is published
- Row-level security rules apply
- Prevents accidental leaking of sensitive reducer arguments

**Reducer Arguments:**
- No longer broadcast to subscribers in 2.0
- Only the calling client sees their own reducer arguments
- Improves privacy and security

## Advanced Features in 2.0

### Subscriptions (Version 2.0.0)

Subscriptions replicate database rows to your client in real-time. When you subscribe to a query, SpacetimeDB sends matching rows immediately and pushes updates whenever those rows change.

**How Subscriptions Work:**
1. **Subscribe**: Subscribe with queries to the data you need
2. **Receive initial data**: SpacetimeDB sends all matching rows immediately
3. **Receive updates**: When subscribed rows change, you get real-time updates
4. **React to changes**: Use row callbacks (OnInsert, OnDelete, OnUpdate) to handle changes

**Key Concepts:**

- **Client Cache**: The client maintains a local cache of subscribed data. Reading from the cache is instant since it's local memory.
- **Typed Query Builders**: Type-safe query builders are available in C# and are the recommended default. They provide auto-completion and compile-time type checking.
- **Subscription Handles**: Subscribing returns a handle that manages an individual subscription lifecycle.
  - `IsActive` indicates that matching rows are currently active in the cache
  - `IsEnded` indicates a subscription has ended, either from unsubscribe or error
  - Unsubscribe is asynchronous: rows are removed after the unsubscribe operation is applied

**Best Practices:**

1. **Write Efficient Subscription Queries**: Use the typed query builder to express precise filters and keep subscriptions small.

2. **Group Subscriptions with the Same Lifetime Together**: Subscriptions with the same lifetime should be grouped together. This improves throughput by reducing data transfer.

```csharp
// Never need to unsubscribe from global subscriptions
var globalSubscriptions = conn
    .SubscriptionBuilder()
    .AddQuery(q => q.From.Announcements())
    .AddQuery(q => q.From.Badges())
    .Subscribe();

// May unsubscribe as player advances
var shopSubscription = conn
    .SubscriptionBuilder()
    .AddQuery(q => q.From.ShopItems().Where(r => r.RequiredLevel.Lte(5)))
    .Subscribe();
```

3. **Subscribe Before Unsubscribing**: When updating a subscription, subscribe to the new set before unsubscribing from the old one. SpacetimeDB subscriptions are zero-copy, so subscribing to the same query multiple times doesn't incur additional overhead.

4. **Avoid Overlapping Queries**: Distinct queries that return intersecting data sets can result in the server processing and serializing the same row multiple times.

### Procedures (Beta)

Procedures are functions similar to reducers but with additional capabilities:

- **HTTP Requests**: Can make HTTP requests to external services
- **Manual Transactions**: Must manually open and commit transactions using `ctx.WithTx()`
- **Return Values**: Can return values to the calling client

**When to Use Procedures:**
- Need to call external APIs (e.g., OpenAI, payment processors)
- Need to fetch data from external services
- Need to combine side effects with database operations

**Example:**
```csharp
#pragma warning disable STDB_UNSTABLE

[SpacetimeDB.Procedure]
public static string FetchExternalData(ProcedureContext ctx, string url) {
    // Make HTTP request
    var result = ctx.Http.Get(url);
    var response = result.UnwrapOrThrow();
    var body = response.Body.ToStringUtf8Lossy();
    
    // Process within a transaction
    ctx.WithTx(txCtx => {
        txCtx.Db.Cache.Insert(new Cache { Data = body });
        return 0;
    });
    
    return body;
}
```

**Important Notes:**
- Procedures are currently in beta and their API may change
- Prefer reducers unless you need HTTP requests or other side effects
- Functions passed to `WithTx` may be invoked multiple times
- Avoid capturing mutable state within `WithTx` functions

### Column Types and Performance

**Type Performance Considerations:**

1. **Prefer smaller types**: Use the smallest integer type that fits your data range (e.g., `byte` instead of `ulong` for values 0-255)

2. **Prefer fixed-size types**: Fixed-size types (`uint`, `double`, fixed-size structs) allow direct memory offset computation. Variable-size types (`string`, `List<T>`) require additional indirection.

3. **Consider column ordering**: Order columns from largest to smallest alignment to reduce padding. For example:
   - `(byte, ulong, byte)` may require 24 bytes due to padding
   - `(ulong, byte, byte)` requires only 16 bytes

**Collections vs. Separate Tables:**

Use a collection column (`List<T>`) when:
- Items form an atomic unit read/written together
- Order is semantically important
- Collection is small and bounded
- Items are values without independent identity

Use a separate table when:
- Items have independent identity and lifecycle
- Need to query/filter individual items
- Collection can grow unbounded
- Clients should receive updates for individual items
- Need referential integrity between items and other data

**Binary Data:**
SpacetimeDB optimizes storing binary data as `List<byte>`. You can store files, images, or serialized data directly in table columns when:
- Binary data is associated with a specific row
- Data should participate in transactions and subscriptions
- Data size is reasonable (up to several megabytes per row)

### Migration-Specific Considerations

**For Your Bus Ticket System:**

1. **Subscriptions**: Your API service should subscribe to all relevant tables and event tables. Consider grouping subscriptions by lifetime (e.g., static data vs. dynamic data).

2. **Event Tables**: Use event tables for cross-client notifications (authentication events, ticket sales, bus status changes). This replaces the old reducer callback system.

3. **Procedures**: If you need to integrate with external payment processors or APIs in the future, use procedures instead of reducers.

4. **Column Types**: Review your table definitions for optimization opportunities:
   - Use `byte` for small enums (e.g., status codes)
   - Use `uint` instead of `ulong` where appropriate
   - Consider fixed-size arrays for bounded collections

5. **JSON Parsing**: The `$id` and `$values` metadata in JSON responses is due to reference preservation. Consider:
   - Using DTOs to avoid circular references
   - Configuring JSON serializer to ignore reference handling
   - Using typed query builders to avoid JSON altogether

## HTTP API Reference (Version 2.0.0)

### Authorization and Identity Generation

SpacetimeDB 2.0 provides HTTP endpoints for identity and token management, which are critical for the custom authentication system used in this project.

#### Identity Generation Methods

**Method 1: POST /v1/identity (Used in this project)**

This is the method currently used for generating unique identities for each user:

```http
POST /v1/identity
```

**Returns:**
```json
{
  "identity": "string",
  "token": "string"
}
```

**Key Points:**
- Generates a new identity and token signed by the SpacetimeDB host
- Token is not portable to other SpacetimeDB clusters
- This is the "jerry-rigged" solution mentioned in the authentication system design
- Used during user registration to create unique identities

**Method 2: Anonymous WebSocket Connection**

Alternatively, a new identity and token will be generated during an anonymous connection via the WebSocket API, passed to the client as an `IdentityToken` message.

#### Authorization Headers

SpacetimeDB HTTP endpoints require or optionally accept a token in the Authorization header:

```
Authorization: Bearer ${token}
```

Where `token` is an OpenID Connect compliant JSON Web Token (such as the one returned from `POST /v1/identity`).

#### Token Derivation

SpacetimeDB can derive an identity from the `sub` and `iss` claims of any OpenID Connect compliant JSON Web Token. This is how the custom authentication system associates JWT tokens with SpacetimeDB identities.

### Key HTTP Endpoints

#### Identity Management

**POST /v1/identity/websocket-token**
- Generate a short-lived access token for use in untrusted contexts (e.g., embedded in URLs)
- Requires: `Authorization: Basic` header with Spacetime token
- Returns: `{ "token": "string" }` (short-lived JWT)

**GET /v1/identity/public-key**
- Fetches the public key used by the database to verify tokens
- Returns: PEM certificate chain
- Useful for token verification in the API layer

**GET /v1/identity/:identity/verify**
- Verify the validity of an identity/token pair
- Requires: `Authorization: Basic` header
- Returns:
  - `204 No Content` if token is valid and matches identity
  - `400 Bad Request` if token is valid but doesn't match identity
  - `401 Unauthorized` if token is invalid

**GET /v1/identity/:identity/databases**
- List all databases owned by an identity
- Returns: `{ "addresses": array<string> }`

#### Database Management

**POST /v1/database/:name_or_identity**
- Publish to a database with the specified name or identity
- Query parameter: `clear` (boolean) - whether to clear existing data when updating
- Requires: `Authorization: Bearer` header
- Data: WebAssembly module in binary format
- CLI equivalent: `spacetime publish`

**GET /v1/database/:name_or_identity**
- Get database information (identity, owner, host type, module hash)
- Returns database metadata

**DELETE /v1/database/:name_or_identity**
- Delete a database
- Requires: `Authorization: Bearer` header
- CLI equivalent: `spacetime delete <identity>`

**GET /v1/database/:name_or_identity/schema**
- Get schema for a database
- Query parameter: `version` (e.g., 9)
- Returns: RawModuleDef in JSON form
- CLI equivalent: `spacetime describe <name_or_identity>`

**POST /v1/database/:name_or_identity/call/:reducer**
- Invoke a reducer OR procedure in a database
- Requires: `Authorization: Bearer` header
- Data: JSON array of arguments to the reducer
- **Important**: This endpoint can call both reducers and procedures

**POST /v1/database/:name_or_identity/sql**
- Run a SQL query against a database
- Requires: `Authorization: Bearer` header
- Data: SQL queries, separated by `;`
- Returns: JSON array of statement results with schema and rows
- CLI equivalent: `spacetime sql <name_or_identity> <query>`

**GET /v1/database/:name_or_identity/logs**
- Retrieve logs from a database
- Query parameters:
  - `num_lines`: Number of most-recent log lines to retrieve
  - `follow`: Boolean; whether to continue receiving new logs via a stream
- Requires: `Authorization: Bearer` header
- CLI equivalent: `spacetime logs <name_or_identity>`

#### WebSocket Connection

**GET /v1/database/:name_or_identity/subscribe**
- Begin a WebSocket connection with a database
- Required headers:
  - `Sec-WebSocket-Protocol`: `v1.bsatn.spacetimedb` or `v1.json.spacetimedb`
  - `Connection`: `Upgrade`
  - `Upgrade`: `websocket`
  - `Sec-WebSocket-Version`: `13`
  - `Sec-WebSocket-Key`: 16-byte value, Base64 encoded
- Optional header:
  - `Authorization`: Bearer token
- Protocols:
  - `v1.bsatn.spacetimedb`: Binary protocol using BSATN encoding
  - `v1.json.spacetimedb`: Text protocol using SATS-JSON format

#### Utility Endpoints

**GET /v1/ping**
- No-op endpoint to test connectivity
- Returns no data
- Used to determine whether a client can connect to SpacetimeDB

### Migration-Specific Notes

**Identity Generation Pattern:**

The current implementation uses `POST /v1/identity` to generate unique identities for each user during registration. This pattern will continue to work in 2.0 without changes:

```csharp
// Current implementation (works in 2.0)
public async Task<Identity> GenerateNewIdentity() {
    var httpClient = new HttpClient();
    var response = await httpClient.PostAsync(
        "http://localhost:3000/v1/identity",
        new StringContent("{}", Encoding.UTF8, "application/json")
    );
    
    var result = await response.Content.ReadFromJsonAsync<IdentityResponse>();
    return result.Identity;
}
```

**Reducer/Procedure Invocation:**

The `POST /v1/database/:name_or_identity/call/:reducer` endpoint can invoke both reducers and procedures. This is important if you decide to use procedures for external API calls in the future.

**Token Verification:**

Consider using `GET /v1/identity/:identity/verify` in the API layer to verify SpacetimeDB identities match the tokens in JWT claims. This adds an extra layer of security to the custom authentication system.

**SQL Access:**

The `POST /v1/database/:name_or_identity/sql` endpoint provides direct SQL access to the database. This can be useful for:
- Data migration from 1.0 to 2.0
- Administrative queries
- Debugging and troubleshooting
